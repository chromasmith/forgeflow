# Visibility Tiers

Forge Flow uses a deliberate information architecture to control what AI coding agents consume. This isn't about file organization — it's about managing context windows for maximum agent effectiveness.

## The Problem

AI coding agents degrade when overloaded with context. A 77,000-line Blueprint file, a 1,000-line session history, and a full API spec crammed into a single prompt will produce worse results than a surgical 50-line excerpt targeting exactly what the agent needs.

Forge Flow solves this by placing files into visibility tiers that determine when and how agents access them.

## Tier 1 — Always Visible

**Location:** Repo root + `.forge/` session files
**Access pattern:** Read automatically at session start
**Who reads:** Claude Code (via CLAUDE.md guidance and Focused Build Protocol)

| File | Location | Why It's Always Visible |
|------|----------|------------------------|
| CLAUDE.md | Root | Entry point — agents always read this first |
| backlog.yaml | .forge/ | Agent needs to know the work queue |
| session-state.yaml | .forge/ | Agent needs to resume from where we left off |
| active-bugs.yaml | .forge/ | Agent needs to know what's broken |
| GOTCHAS.yaml | .forge/ | Agent needs to avoid known pitfalls |

These files are intentionally kept small and focused. Together they should give an agent full situational awareness in under 500 lines.

session-history.yaml is also read at session start for recent context, but agents don't need the full history — just the last few entries for continuity.

## Tier 2 — Read When Pointed

**Location:** `.forge/specs/`, `.forge/style/`, `.forge/blueprint/Blueprint-manifest.yaml`
**Access pattern:** Read only when the captain includes them in a focused prompt
**Who reads:** Claude Code (via surgical prompt references with file paths and line numbers)

| File | When It's Needed |
|------|-----------------|
| specs/api-spec.yaml | Building or modifying API routes |
| specs/deployment.yaml | Deployment or infrastructure work |
| specs/integrations.yaml | Working with external services |
| specs/testing.yaml | Writing tests or QA work |
| specs/[project-specific].yaml | Domain-specific tasks |
| style/tokens.yaml | UI/styling work |
| Blueprint-manifest.yaml | Checking implementation progress |
| chromaswarm.yaml | ChromaSwarm sessions only |

The captain (Claude Web) reads these files, extracts the relevant sections (often just 20-50 lines), and injects them into the focused prompt with exact file paths and line numbers. The agent never loads the full file.

## Tier 3 — Never Auto-Read

**Location:** `.forge/blueprint/Blueprint.yaml`
**Access pattern:** Never loaded by agents. Captain provides surgical excerpts only.
**Who reads:** Claude Web (the planning AI, which holds full project context)

| File | Why It's Blocked |
|------|-----------------|
| Blueprint.yaml | Too large (2,000+ lines, 70KB+). Loading it would consume the agent's context window and degrade performance on the actual task. |

This file is explicitly listed in CLAUDE.md's "DO NOT READ" section. The captain reads it during planning and extracts only the sections relevant to the current task — a database schema fragment, a specific feature spec, an API contract — and includes that excerpt in the focused prompt.

## Tier 4 — System Output (Not Forge Flow Files)

These files are generated by external tools and are not part of the Forge Flow specification, but agents may encounter them:

| File/Directory | System | Agent Behavior |
|---------------|--------|----------------|
| .chromaqa/ | ChromaQA | Read debt file at session start if threshold exceeded |
| chromaswarm-friction-journal.yaml | ChromaSwarm | Never read during build sessions |
| chromaqa-check.sh | ChromaQA | Execute when running quality gates |

## How the Captain Uses Tiers

The captain/agent workflow leverages tiers at every step:

**Session start:** The Focused Build Protocol reads Tier 1 files and provides a status summary. If ChromaQA debt exceeds threshold, the captain alerts the user.

**Task planning:** The captain reads Tier 2 and Tier 3 files as needed, extracts surgical excerpts, and builds a focused prompt containing only what the agent needs.

**Task execution:** The agent works with Tier 1 context (always available) plus the surgical excerpts injected by the captain. It never loads Tier 2 or Tier 3 files on its own.

**Session end:** The captain generates updated content for all Tier 1 files and produces a single prompt for the agent to write, commit, and deploy.

## Controlling Visibility in CLAUDE.md

The `.forge/ Documentation` section of CLAUDE.md is where tiers are enforced:

    ## .forge/ Documentation

    **DO NOT READ:**
    - `.forge/blueprint/Blueprint.yaml` — Too large.

    **SAFE TO READ (when relevant to your task):**
    - `.forge/GOTCHAS.yaml` — Friction lessons. Check when you hit unexpected issues.
    - `.forge/session-state.yaml` — Current session context
    - `.forge/backlog.yaml` — Work queue
    - `.forge/active-bugs.yaml` — Known bugs and their status
    - `.forge/specs/api-spec.yaml` — API documentation
    - `.forge/specs/integrations.yaml` — Third-party services
    - `.forge/style/tokens.yaml` — Design system

This section should be updated as new files are added to `.forge/`.
